# 数据构造质量门槛

## 能力与场景

- 先有能力地图，后有场景计划。能力回答“Agent 替用户完成什么”，场景回答“在哪个已证实条件下它会走不同决策路径”。
- 不能用数据来源、工具名、卡片类型、字段名或错误类型充当能力名称。
- 将规则分成能力、能力分支、通用约束和处理边界。为得出结果而进行的分析、候选筛选或字段填充，若不是用户可独立获得的结果，就不是独立能力；影响多项能力的真实性、权限、去重、数量或格式规则，也不是独立能力。
- 每个场景必须指出所属能力、规则来源和相邻场景的判别点；无法指出时，合并为同一场景的样本变化，或标为待确认。
- 覆盖以确认后的能力地图为准，不以固定分类、固定比例或场景数量为准。

## 一致性

- 每条 case 建立可追溯链：事实、规则、输入、处理过程、证据、预期动作和标准答案彼此对应。
- 每个事实性字段都记录来源：代码、规则、fixture、数据源、trace 或用户确认。来源不存在时不编造。
- 只有 Agent 实际可见的事实、状态和证据才能出现在处理过程或标准答案中。
- 存在状态变化时，按发生顺序记录状态和证据；不要使用一个静态快照代表不同时点。
- 多轮或多处理单元时，每轮依据实际命中的 Prompt、规则和输出协议构造。
- 对已确认的输入变体，只改变该变体规定可以变化的字段；原始事实、规则、标准意图和执行证据仍保持可追溯。
- 只组合当前实现允许共同出现的维度；没有证据支持的组合不生成。
- 规则、数据或当前实现无法唯一决定金标时，标为“待用户确认”，不要靠常识补全。

## 验证

- 记录 Prompt、接口/工作流/知识库、规则、fixture 或数据源、生成模型和 case plan 的版本；任一依赖变化时标记相关 case 需要复验。
- 将不合格样本写入拒绝集，禁止“重试耗尽后仍写入最后一个样本”。
- 使用中文写场景、应有表现和失败原因；不要使用抽象用途标签替代具体用户情况。
- 结构校验：JSONL 格式、必填字段、类型、唯一 ID、引用完整性。
- 链路校验：输入、参数、状态、外部结果和标准答案与 case plan 一致；能执行的链路在 fixture 上复现。
- 语义校验：回复符合当前 Agent 的 Prompt、业务规则与输出协议；不要使用参考回复逐字匹配代替语义判断。
- 先校验 sample；获得用户确认后才扩充 formal，并在 formal 落盘后重新校验。
