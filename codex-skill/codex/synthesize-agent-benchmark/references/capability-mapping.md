# 能力地图与场景计划

能力地图是内部审计文件，不要求用户填写。构造者从代码和规则中写入，用户只需审核业务描述和覆盖范围。

## 文件结构

```json
{
  "Agent": "…",
  "评测边界": "只测目标 Agent / 包含上下游处理单元",
  "证据": ["相对路径或规则标识"],
  "通用约束": [
    {
      "名称": "跨能力规则名称",
      "适用能力": ["能力名称"],
      "规则": "会影响哪些决策，但不构成独立用户目标",
      "规则来源": ["文件路径、测试名或 trace 标识"]
    }
  ],
  "能力": [
    {
      "名称": "动词+对象的能力名称",
      "用户目标": "用户希望解决什么",
      "触发与前提": "什么输入和条件会进入这项能力",
      "可见信息与依赖": ["目标 Agent 实际可见的数据或上游结果"],
      "处理与预期行为": "依据何规则产出什么结果",
      "相邻能力边界": "何时属于另一项能力或另一处理单元",
      "规则来源": ["文件路径、测试名或 trace 标识"]
    }
  ],
  "场景": [
    {
      "名称": "具体用户情况",
      "能力": "所属能力名称",
      "用户情况": "用户说什么、处于什么业务情况",
      "关键条件": "会改变处理路径的事实或状态",
      "预期行为": "应答、外部动作、转交或状态变化",
      "与相邻场景的判别点": "哪条规则使两者金标不同",
      "规则来源": ["文件路径、测试名或 trace 标识"]
    }
  ]
}
```

## 归类方法

先从用户视角写出目标，再反推 Agent 的判定和输出。先将每条规则归为：能力、能力分支、通用约束或处理边界。一个能力不因读取两个数据源、生成两种表达、做一次内部分析或填写两类字段而拆分。只有用户目标不同，或同一目标会进入不同的决策规则、输出契约、外部动作或交接对象时，才拆分。

特别检查“中间步骤被误当能力”的问题：若 A 只是为了得出 B 而进行的分析、筛选或校验，并且用户不能单独要求或获得 A 的独立结果，A 是 B 的处理过程。若同一规则会限制多个能力，它是通用约束，记录在 `通用约束`，并在相关场景中做对照，不要拆成单独的能力或场景。

场景是能力的决策分支。为每个场景写一句“若关键条件从 A 变成 B，为什么金标必须变”；写不出来时，通常应合并为同一场景的 fixture 或话术变化。不要为了凑覆盖而把每个异常、每张卡或每个字段单列成场景。

无法从现有规则确定边界时，保留“待用户确认”，不要用经验替它命名或补金标。
