# 智能体评测数据构造

用自然语言接收需求。通用的是探索方法、能力建模和数据一致性门槛，不是预置 case 清单。不要把任何特定 Agent 的场景、字段、工具、错误类型或交互方式当作默认要求。

## 用户怎样发起

用户不填写 YAML、表格或 case 配置。接受一句口述需求，例如：

```text
帮我构造“司机查询奖励和热区”的离线评测数据；相关 Prompt、工具定义和业务规则在 ./agent_bundle。
```

```text
构造查询 Agent 的数据，先帮我探索场景；目录在 ./backend/agents/search，先不要生成数据。
```

用户可补充已有 badcase、期望先试的 sample 数量、已有 JSONL schema 或不能覆盖的范围；未提供时主动询问或从项目中探索。不要要求用户先枚举能力、场景、比例、工具、历史结构或 JSON 字段。

首次回复只说明将要阅读的资料和评测边界；完成探索后，先以具体中文场景请用户确认。任何数据生成都在明确确认后进行：先生成 sample，用户审阅通过后才生成 formal。用户只说“先试 50 条”时，50 条就是本次 sample，不追问 formal 数量，也不擅自生成 formal。

## 1. 确定评测边界并收集证据

将“构造某个 Agent 的数据”理解为 Agent 级；将“构造某业务场景的数据”理解为场景级。用户同时给出两者时，以场景级为准。先明确评测边界：只测目标 Agent，还是连同路由、上游改写、下游执行一起测。默认只测目标 Agent；跨处理单元的行为只记录为依赖证据，不混为目标 Agent 的金标。

读取目标相关的 Prompt、接口定义、业务规则、运行代码、状态/会话逻辑、测试、已有 case 和脱敏 trace。可先运行：

```bash
python3 scripts/inspect_agent_bundle.py --root <目标目录> --output <审计目录>/Agent探索结果.json
```

脚本只做文件盘点和框架线索识别，不能代替阅读代码。先画出交互链：用户输入从哪里进入，经过哪些处理单元，目标 Agent 实际能看到什么，它交给谁或输出什么。不要仅凭目录名、工具名或数据表名猜测能力。

需要判断工具、RAG、工作流、路由等实现差异时，阅读 [references/agent-frameworks.md](references/agent-frameworks.md)。

## 2. 先建立能力地图

不要一读到数据字段或卡片协议就开始列场景。先把代码和规则归纳为“这个 Agent 替用户完成什么事”，并写入内部 `能力地图.json`。一项能力必须有独立的用户目标和独立的处理结果；名称使用动词和对象，不使用数据来源、卡片类型、接口名或异常标签。

先把每条规则归入四类：能力、能力分支、通用约束、处理边界。只有能力才可作为场景的顶层分组。为了得出某个结论而读取数据、做诊断、筛选候选或填充输出字段，若它不是用户可独立获得的结果，就只是该能力的处理过程或证据，不能另列一项能力。例如，若 Agent 的契约是“根据当前事实给出处理建议”，事实分析和建议属于同一能力；只有代码允许用户单独获取分析结果、且其输出契约不同，才拆成两项能力。

每项能力必须写清：

- 用户要解决什么；什么输入会触发它。
- Agent 实际可见哪些信息，依据哪些规则判断。
- 它会产出什么行为或结果；结果会交给哪个下游处理单元。
- 前提不满足、规则不覆盖或属于相邻 Agent 时，实际会怎样处理。
- 与相邻能力的分界规则，以及代码、Prompt、测试或 trace 证据。
- 影响多项能力的通用约束，例如事实真实性、历史去重、权限、输出数量或格式限制；将其作为跨能力规则记录，不要单列为能力。

同一用户目标、同一判定规则、同一预期行为，即使会读取不同数据或使用不同卡片，也属于同一能力下的不同条件，不要拆成两项能力。不同数据源只有在它会改变处理规则、输出行为或下游动作时，才成为新的场景分支。

使用 [references/capability-mapping.md](references/capability-mapping.md) 的字段和判定方法，完成后运行：

```bash
python3 scripts/validate_capability_map.py <审计目录>/能力地图.json --stage capability
```

## 3. 从能力地图推导互斥场景

对每项能力，从真实代码和规则中找出会改变行为的条件分支，再生成场景。场景的定义是：**同一能力下，用户目标与关键条件确定后，Agent 应走的一条不同决策路径**。数据值、同义表达、文本噪声和历史轮数本身不是场景；只有它们导致规则、输出、外部动作、路由或金标不同，才是新的场景。

为每个场景写明：用户情况、关键条件、预期行为、规则来源，以及“它与哪个相邻场景不同、不同在哪里”。在场景加入计划前逐对检查：

- 两个场景的预期行为和金标相同，且只有输入措辞或事实取值不同：合并为一个场景，在该场景内扩展样本。
- 两个场景的用户目标相同，但某个已证实的规则分支会让输出、外部动作、路由或允许范围改变：保留为两个场景，并写出该判别规则。
- 没有规则或 trace 能判断差异：标为“待用户确认”，不能借常识强行拆分。

这一步的目标是覆盖决策空间，不是把所有数据表、卡片、错误输入各列一遍。将已确认的场景写回 `能力地图.json`，再运行：

```bash
python3 scripts/validate_capability_map.py <审计目录>/能力地图.json --stage scenario
```

## 4. 用具体能力和场景请用户确认

在生成前，用业务同学能看懂的语言汇报。先解释 Agent 的能力边界，再展示每项能力下不重复的场景。不要用“正常/边界/对抗/回归”等抽象标签，也不要展示通用默认 case 清单。

```text
我理解这个 Agent 是替用户解决……；它不负责……，这部分由……处理。

能力一：<用户目标>
- 什么时候由它处理：<触发与前提>
- 它依据什么判断：<真实可见的数据和规则>
- 最终会怎样：<预期行为与下游动作>

该能力下计划覆盖：
1. <具体用户情况>
   例如：<用户自然说法>
   与相邻场景的区别：<触发不同决策的规则>
   应有表现：<具体行为>

待确认：<规则未定义或证据不足的具体情况>。

计划先生成 sample：<按确认场景动态计算的数量> 条；确认 sample 后再生成 formal：<动态计算的数量> 条。
你还希望补充哪些真实会问、容易出错或线上常见的情况？
```

不要将任何数量写死。根据已确认能力、场景分支、必要的最小对照组和事实变化动态计算数量。用户指定“先试 50 条”时，只生成 50 条 sample，不擅自安排 formal。等待用户明确确认后才生成 sample；sample 审阅和修订确认后才生成 formal。

## 5. 先确定事实链，再生成自然语言

为每个已确认场景先写 case plan。每条 plan 只记录当前 Agent 实际支持的内容：事实和来源、规则和来源、初始状态、输入、处理路径、执行证据、预期动作与标准答案。没有对应维度时省略，不要为了统一格式虚构它。

所有 case 都要满足这条链：

```text
已声明的事实与规则 → Agent 实际可见的输入和状态 → 实际处理路径 → 可追溯的证据 → 预期动作与标准答案
```

每一个事实、历史内容、状态、业务标识、外部结果和标准答案都必须能追溯到 plan 中声明的来源。不要为了让 case 看起来完整而补造缺失事实、伪造历史、伪造执行结果，或让答案引用 Agent 看不到的信息。规则不能判定时，停止生成该 case 并标为“待用户确认”。

LLM 只生成自然的用户表述、历史台词和参考回复；它不能自行决定规则、事实、执行路径、外部能力调用或金标。若一段历史由多个处理单元产生，各轮分别遵循实际命中的 Prompt、业务规则和输出协议。

## 6. 生成、验证与交付

最终产物必须为 JSONL，一行一个 case。字段和分类值优先使用中文；工具名、参数键、状态码等必须与真实协议对齐的技术字面量保留原样。已有运行器依赖英文键时保留兼容键，同时增加中文人工审核字段，不破坏运行器。

每条记录至少包含：样本 ID、Agent、能力、场景、用户情况、应有表现、历史对话、事实数据、用户输入、标准意图、预期动作、执行证据、标准答案、校验和版本信息。具体字段以当前项目 schema 为准；不通过的样本写入独立 `rejected.jsonl`，记录中文失败原因。

使用脚本创建内部审计目录和运行清单：

```bash
python3 scripts/init_benchmark_run.py \
  --output-dir <输出目录> \
  --agent <Agent名称> \
  --scope <场景描述> \
  --sample-count <已确认的动态数量>
```

只有用户已经确认本次需要 formal 时，才额外传入 `--formal-count <已确认的动态数量>`。先让真实工具、检索器、工作流或路由逻辑在 fixture 上执行，并与 case plan 中的执行证据差分校验。再运行：

```bash
python3 scripts/validate_jsonl.py <sample.jsonl> --strict --write-report <校验报告.json>
python3 scripts/report_coverage.py <sample.jsonl> --capability-map <审计目录>/能力地图.json --output <覆盖报告.json>
```

通用脚本只能检查结构、覆盖和基础跨字段关系，不能证明业务语义正确。针对已确认场景补充业务校验。sample 通过后，展示典型样本、未覆盖项、拒绝样本和 formal 数量计划，请用户确认；formal 完成后再次校验并交付 JSONL、拒绝样本、能力地图、审计清单和报告。

构造和校验时阅读 [references/quality-gates.md](references/quality-gates.md)。
