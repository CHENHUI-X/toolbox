# macOS 应用代理排查

确认真实网络路径，再用最小改动解决问题。用户不能开启 TUN 时只考虑显式代理；系统代理开启不等于应用后台已走代理。

## 先诊断再修改

1. 确认应用名称、路径、版本、报错及相关后台进程。区分 Antigravity 独立应用、IDE 和 CLI，不能混用教程。检查当前版本本机实现，区分官方说明和社区经验。
2. 在真实主机读取 `scutil --proxy`、代理客户端进程和实际端口。沙箱返回空代理或无法列出进程时，不能据此判定主机没有代理；通过允许的主机访问方式复核。
3. 对报错目标做不携带账号凭据的直连和显式代理对比，设置连接及总请求超时。401、404、405 等仅证明得到 HTTP 响应，不能证明登录成功；也不能单凭 403 归因到地区限制。
4. 检查真正发起请求的后台，不只检查界面主进程。用 `lsof -nP -a -p <PID> -iTCP` 核对代理连接；必要时只读代理客户端连接接口，匹配域名、源端口、规则和出口节点。

代理环境变量缺失不等于没走代理，应用可能使用系统代理或自己的配置。若连接已通向本机代理并命中代理出口，继续调查请求失败、长连接或会话重连，不重复套用补环境变量的修复。

## 选择持久方案

- 优先使用应用支持的持久代理设置，确认其覆盖登录和网络后台。
- 应用明确读取 shell 环境时，先检查已有配置；已经正确且持久就核验并停止修改。新增前确认 shell、启动文件及变量覆盖顺序。
- 用户需要原图标且只影响该软件时，仅在能可靠识别调用应用的前提下使用有条件的 shell 配置，验证普通终端和其他应用不会命中。无法可靠限定就说明限制，不声称隔离已实现。
- 独立启动入口仅用于更简单方案不成立且符合用户启动要求的情况；说明原图标不会因此自动附带代理参数。

不要优先修改安装包的 Info.plist、app.asar 或二进制：可能影响签名并被更新覆盖。没有读取证据时不要随意给 settings.json 添加配置键，不关闭证书校验来掩盖网络故障。

只设置实际需要的变量。常见 HTTP 代理为 HTTP_PROXY、HTTPS_PROXY，必要时兼容小写；ALL_PROXY 是否需要及协议由客户端决定。配置环境代理时保留 localhost、127.0.0.1、::1 直连并合并已有 NO_PROXY 例外。

修改前备份相关文件，保留无关内容。已有全局 shell 代理不能描述为只影响这个应用，也不能未经授权删除。更新或重装后重新核验，不承诺永久兼容。

## Antigravity 已验证机制

2026-10-09 本机独立应用 2.21.1 的后台环境构造为：

```javascript
const env = { ...process.env, ...shellEnvSync() };
```

所带 shell-env 以 `-ilc` 读取 shell 环境，再传给 language_server。当时本机 .zshrc 已有持久代理，主进程没有 HTTP_PROXY，但后台继承了代理且实际连接 Clash。因此原图标启动可能通过已有 shell 配置生效；不能只检查主进程，也不能推广为所有版本的官方承诺。

当时端口为 127.0.0.1:7897，后续必须核对实时端口。条件式 shell 配置仅是候选方案，本次案例没有实际实施或验证，不能写成已验证方案。

## 验证与交付

最多保留三项必要验证：配置有效；按用户实际启动方式启动后后台真实走代理；原故障恢复或明确账号步骤尚未验证。满足目标就停止改动。退出应用前检查任务状态，避免中断用户工作。

界面工具超时后先检查应用、控制服务或连接状态，再恢复一次，不反复操作过期对象。无法读取界面时可继续进程和网络诊断，但不能声称登录成功。

读取进程环境时只输出代理相关键。不要打印完整 ps eww、shell 配置、认证数据库或含令牌的日志；含认证信息的代理 URL 也需要脱敏。

用户问能不能、搞好了吗时，先直接回答完成状态，再简短说明核验结果、实际改动和适用范围。区分已有配置、本次修改、网络连通、登录成功，不把推测说成完成。

清理时删除本次创建且用户要求移除的入口、脚本和副本，并确认目标不存在；保留系统代理、代理客户端、账号资料及无关配置。
