# Benchmark Case 构造方法论

通用方法论，不绑定任何具体仓库/项目/Agent。每次在新项目里使用时，涉及具体文件路径、具体代码、具体类目/词典内容的部分都要现场探查/新建，不要假设某个固定路径或内容存在。

## 这个 skill 管什么、不管什么

**管**（怎么构造一条 case，涉及的角度）：
1. 怎么正交枚举出一批 case 规格（CaseSpec 驱动的生成架构）
2. 历史对话怎么搭（结构/数据自洽/指代自然度/校验兜底四层约束）
3. 当前轮 user_input 怎么注入语言噪声（ASR错别字/同音字/口语化/含糊指代等）
4. 边界/兜底测试池怎么设计（路由错误、越权诉求、事实偏离、敏感内容拒绝等）
5. 输出 schema 怎么设计（权威评估字段 vs 参考字段怎么分）
6. 协作与调试流程（怎么跟用户对齐设计、怎么定位和修复 LLM 生成的问题）

这些角度彼此独立又互相咬合，共同构成"怎么把一批 case 从无到有、可控、可复现地生成出来"这件事的完整方法论，与具体测哪个 Agent、测它的哪个能力无关。

**不管**（每次现查/现建，不是 skill 内容）：
- 目标 Agent 到底有哪些能力、每个能力该拆成哪些具体 case_category、固定兜底话术是什么——必须每次现读现得。先探查清楚"这个 Agent 的能力契约实际长在哪"（系统 Prompt？工具/函数定义？某种 schema 文件？不要假设格式，不同项目差异很大），再基于真实契约设计类目，不能自己编。
- 领域词汇的错别字/同音字/口语化词典的**具体内容**、以及边界测试池里"越权诉求""能力范围外"等类型的**具体示例措辞**——现场根据当前 Agent 的领域构建。同一项目里如果之前已经建过（给别的 Agent 做过 benchmark），复用并增量扩展，不必每次重来；跨项目没有复用基础，从零建。

一句话：这个 skill 教你怎么把"内容"（case_category、固定话术、领域词、示例措辞——这些每次现查）组装成一批**分布可控、结构合法、数据自洽、语言自然、边界清晰**的 benchmark case。

## 使用流程

1. **发现有没有"前人产出"可以复用**（自动做）：当前项目里如果已经存在按这套方法论产出的 benchmark 代码（不管是不是给同一个 Agent 建的），先读一遍，复用它的模块结构、复用/扩展它的领域词典，不要从零重写；如果是这个项目第一次用这个 skill，才从零搭。
2. **定位能力契约**：探查目标 Agent 的能力/工具契约实际定义在哪（不要假设固定文件名/格式），读清楚每个能力支持什么、不支持什么、有没有固定的异常/兜底话术。
3. **发现其他 Agent**（自动做，不问用户）：如果被测 Agent 所在的系统里还有别的协作 Agent（多 Agent 系统常见），扫描它们的角色定义所在位置，找出历史对话里可能混入的其他角色；单 Agent 系统跳过这步。
4. **整理设计草案**：把"正交维度怎么定义（case_category / 轮次分布及各档位配比 / 语言风格及各子类配比 / 追问 / 角色混合）""边界测试池怎么分类型、各子类型名额怎么配比""输出 schema 打算怎么设计"整理成一份完整草案，摆给用户审。
   ⚠️ **强制停顿点**：草案整理完必须停下来，把草案完整展示给用户，明确等待用户的回复再继续，不能自己判断"看起来没问题"就直接往下写代码或生成数据；用户没有回复之前，不允许开始写生成脚本、不允许调用 LLM 批量生成任何 case。
5. 用户确认/纠偏后，按下面的方法论搭建生成模块（或复用第1步找到的既有实现）。
6. 小规模验证 → 发现问题定位修复 → 干净后全量生成，具体怎么做见"六、协作与调试流程"（不重复展开）。

## 一、总体架构：CaseSpec 驱动的生成流程

核心思路：**把"生成规格"和"生成内容"拆成两个独立阶段**——先用确定性代码枚举出一批"case 规格"（每条规格描述这条 case 该具备哪些属性，但不包含具体文本），再逐条把规格交给 LLM 去填内容。这样做的好处是分布保证（比如"3-5轮历史合计占比≥75%"这种硬指标）由代码保证，不用赌 LLM 生成的统计结果恰好符合要求。

一条"规格"通常包含：内容类别（category/fallback_type）、历史轮数、语言风格、是否追问、其他类别专属参数（比如某条 case 需要固定的时间范围、固定的业务状态等，用一个自由字典装）。

> **术语约定**：全文"轮/轮次"统一指**一对 user+assistant 消息**（不是单条消息）。"3轮历史"＝历史里有 3 对 user+assistant、共 6 条消息，当前轮再另加 1 条 user 消息触发本次待评估的回复。后面所有提到"历史轮数""最后一轮"的地方都按这个单位理解。

枚举这批规格时，不同维度用不同的分配技术：

- **精确配额（最大余数法）**：适用于有硬性比例要求的维度（比如历史轮数分布）。先按权重算出每个取值的浮点份额，取整数部分，再把因取整损失的名额按小数余数从大到小补给对应取值，保证总数精确等于目标值、且整体比例严格符合要求。这个技术的价值在于**可复现、总数不会因为四舍五入对不上**。
- **加权随机采样**：适用于自由度更高、只要求"看起来符合自然分布"的维度（语言风格、是否追问）。这类维度通常还需要**条件降级规则**——比如某个风格要求"历史轮数≥1才成立"，采样命中但条件不满足时自动降级成另一个不依赖历史的风格，而不是硬生成一个逻辑不成立的 case。

**"角色混合"不是这种要采样"取哪个值"的维度，不需要配额/采样技术**：它是历史构造内部的一条**结构性约束**（"历史轮数达到某阈值时，混入的协作角色风格种类数不能少于N"），属于二·层①骨架约束的一部分，直接在生成指令里写死这条规则即可，不需要单独进 CaseSpec 枚举表、也不用纠结该用最大余数法还是加权采样。

**轮次分布是精确配额技术最典型的应用场景，通常设计成"档位 + 集中度"结构**：不是从 0 到 N 均匀取值，而是先按业务含义切出几个档位——常见切法是「无历史（0轮，测试零上下文下能否独立成立、不能有任何依赖历史的推断）」「短历史（1-2轮，测试基本的上下文衔接/最简单的指代）」「多轮历史（3轮及以上，测试真实场景里最常见的连续追问/信息纠缠状态）」——再给各档位定权重，让"最贴近真实高频使用场景"的那个档位拿大头（比如"3-5轮合计占比 ≥ 75%"这类硬指标），边缘档位（0轮、超长轮次）保留非零比例但不必等权，因为边缘档位的价值是**验证边界行为正确**而不是模拟"平均情况"。要不要分档、切几档、各档权重多少，仍然是每个项目自己的业务判断，必须在设计草案里明确写出具体档位和比例交给用户确认（呼应下面"强制停顿点"）；但"分档 + 给主档定集中度，用最大余数法保证精确达标"这个设计动作本身是通用方法论。0轮档位天然会联动降级规则——依赖历史的噪声子类（含糊指代等）在 0 轮档位下必须自动降级，这是"档位设计"和"三、噪声构造"里条件降级规则的交汇点，两处要联动检查，不能只在噪声那一侧堵。

**正交性黄金法则**：以上所有维度必须能自由组合，不能做互斥分桶——一条 5 轮历史的 case 完全可以同时是"错别字风格 + 历史里混了别的协作角色的真实回复 + 追问上一轮话题"。

**耦合检测法**：真实踩过的坑——曾经把"追问"这个结构维度和"内容支不支持"这个内容维度耦合在了一起（规定"追问必须追问一个不支持的字段"），后来拆开成互相独立。判断两个维度是否真正正交，有个通用测试：**如果维度A的实现细节里出现了任何提及维度B取值的条件分支，说明耦合了，需要拆开**。

## 二、历史对话构造四层约束

### 层① 骨架约束（结构层）

- 用**编号骨架**逐条列出角色（"第i轮 user / 第i轮 assistant"），比纯文字描述"必须N轮"有效得多；再配一道事后截断兜底（仅当截断后前缀仍合法交替时才截；追问类 case 不能截，会砍掉铺垫）。
- role 严格交替，第一条 user、最后一条 assistant。
- 历史里混哪几种"角色风格"（取决于这个系统有几个协作 Agent，比如：闲聊、其他能力型 Agent、操作型 Agent、申诉/工单型 Agent……），每种风格的**真实输出格式必须以对应 Agent 的真实系统 Prompt 原文为准**，不能让 LLM 自己编格式；轮数较多时要求混合 ≥2 种风格，不能全是同一种或全是闲聊。
- 追问结构（最后一轮历史铺垫话题，当前轮顺着问）——纯粹的"结构续接"标记，必须和"话题本身答不答得上"完全解耦（见上面"正交性黄金法则"的教训）。

### 层② 数据自洽约束（世界观层，踩坑最多的一层）

历史对话必须和"这个 case 唯一的数据快照"完全自洽，这份数据在整个 case 内（历史所有轮 + 当前轮）固定不变，不是各轮各自编：

- **不能正向捏造**：不能编出快照里不存在的实体/ID/数值。
- **不能反向捏造**：更隐蔽的一个方向——不能矢口否认快照里明明存在的东西（比如快照里某资源是非空的，历史却有一轮说"暂时没有"）。固定兜底话术**只能在对应字段真实为空时使用**，不能因为省事就套用错状态，否则会出现"上一轮刚说没有、下一轮又说有"这种历史内部自相矛盾的 case。
- **动作应该影响状态**（常见的开放问题，遇到时优先设计）：历史里如果发生过状态变更动作（比如打开了某个开关、接受了某个任务），理论上"当前"快照该体现这个变更已生效——如果只做"数据锚定"没做"动作后状态同步"，容易出现"历史刚执行完操作，当前状态却显示操作前的样子"这种矛盾。
- **渐进式状态必须可见**：如果同一件事要靠多轮逐步展开（比如翻页式地展示列表、逐步升级的处理流程），历史里必须让"渐进过程"真实可见（第1步→第2步→第3步依次展示），不能凭空跳到中间/最后某个状态却没有前置记录——被测工具本身通常没有记忆，能不能判断"这是第几次问/第几步"完全依赖对话历史里真实出现过的记录。**这一条容易在代码层面也埋雷**：如果"进度到第几步"这个参数是独立随机采样、跟"历史实际有几轮"没有约束关系，就会出现代码本身在制造凭空跳级的 case——采样时就要让这个参数受历史轮数和真实数据量双重约束。

### 层③ 指代与自然度约束（语言层）

- **含糊指代要有真先例**：指代目标必须在历史某处真实出现过，但不必是紧邻的上一轮——可以跳过 1-2 轮无关内容再指代（"就近指代"，不是"指代上一轮"）。
- **先例必须唯一**：历史最后一两轮不能意外引入第二个同等地位的候选对象，否则指代词没法唯一判断所指。
- **"真无法消歧"是单独一类 case，不属于这一层**：如果按 case 设定指代对象天然没法唯一确定，不该用"含糊指代"这个风格硬造一个所答非所问的"正确答案"——这种情况应该走边界测试池里专门的、故意让最后一轮同时引入两个不相关话题、要求模型反问澄清的构造方式（见下面"四、边界/兜底测试池设计"），和"能消歧但写得像不能"是两类不同的 case，不能混。
- **禁止车轱辘话**：同一事实被多次问到时，后一次回复不能逐字复读前一次原话，要像真实模型一样换一种自然说法（比如明确说"这和刚才说的一样"），不能机械重复。

### 层④ 校验兜底层

每条硬约束尽量配一个**轻量、启发式**的自动校验，不追求 100% 语义精确，但要能兜住"指令没生效"的残留 case：

- ID 类参数子串匹配（history 里出现的 ID 是否在数据快照序列化文本里能找到）→ 抓正向捏造。
- **固定空状态话术 × 对应字段实际非空** 的交叉检查（历史文本命中了某个"暂无/查不到"之类的固定兜底句式，但数据快照里那个字段其实非空）→ 抓反向捏造。这条比正向捏造弱（依赖固定话术是否好匹配），命中不了的兜底话术要如实记录在"不管"清单里，提醒使用者这部分更依赖人工抽查。
- 领域关键词是否在历史全文出现过 → 抓"指代对象缺失"（先例不存在）。
- 最后一轮里不同资源类型/卡片类型的计数 → 抓"指代对象不唯一"。
- 顺序比对（期望的渐进序列 vs 实际出现的序列）→ 抓"凭空跳级"。
- **相邻两次同主题回复的文本相似度**（简单到可以用最长公共子串/编辑距离比例）超过阈值 → 抓车轱辘话（逐字复读）。这条同样是弱信号，语义上换了说法但字面仍然相似的正常表达可能被误伤，建议只用来标记"疑似"，不自动判失败。

**通用原则**：重试几次（2-3次）仍不过校验时，**如实标记进结果的 validation/issues 字段，不静默丢弃这条 case**——残留失败率保持透明，比强行让它"看起来通过"更重要。

## 三、当前轮语言风格 / 噪声构造

这部分是"linguistic_style"这个正交维度的具体实现，严格说不是"历史"，是"当前轮 user_input 怎么写"，但其中"含糊指代"这个子类直接依赖上面层③（要有真先例、先例要唯一），实际使用时几乎总是和历史构造模块一起设计、一起传参（比如要把历史轮数传给噪声选择逻辑，判断"含糊指代"这个子类当前成不成立）。

- **不要在代码里做字符级别的字符串替换/正则替换来注入噪声**——生成出来的噪声会显得生硬、不成体系、容易被下游模型一眼识破是规则替换出来的。正确做法是把"该写成什么风格 + 候选词表 + 硬约束"整理成一段自然语言指令，塞进生成 Prompt，交给 LLM 按指令把 user_input 写成对应风格——噪声更自然、更贴近真实语料。
- **常见风格维度**（供参考，具体取舍/是否需要"同音字"这类跟语言相关的子类，看目标语言和场景）：清晰规范 / 口语化（语气词）/ 简短（省略主语）/ 长句冗余（信息重复但意图仍明确）/ 语音识别错误（见下方单独展开）/ 同音字近音替换 / 含糊指代（依赖历史，见层③）/ 含糊指代+错别字叠加。
- **ASR 识别错误要按"错误严重度"单独分档，不能当成一个笼统的风格**：语音转文字的错误天然有轻重之分——轻度是"单字/单词被识别成形近音近字，句子结构和大部分语义仍完整可读"，重度是"连续几个字被跨字重组/整段识别错位，需要结合上下文才能猜出原意，甚至个别片段读者也存疑"。这两档测的是被测 Agent 完全不同的鲁棒性能力（轻度测"能不能容错识别关键信息"，重度测"能不能在证据不足时正确反问而不是硬猜"），必须拆成两个独立子类分别定权重和校验预期，不能笼统写一条"语音识别错误"就完事——重度那档的 reference_answer 甚至可能不是"正确回答"而是"反问澄清"，这点需要在设计草案里对用户挑明。
- **正交随机采样**：各风格按权重采样，不是互斥分桶；"含糊指代"类子类必须历史轮数≥1才成立，不满足时**自动降级**为其他噪声子类，不能强行造出一个没有先例的含糊指代 user_input。
- **噪声只能出现在 user_input**：历史其他轮次、期望输出、固定兜底话术等一律用标准词——这条边界很容易被 LLM 顺手忽略（比如把错别字带进了 reference_answer），生成指令里要显式强调。
- 领域词的错别字/同音字候选表内容属于"现场建/复用"，不属于 skill；方法是构建"轻度/重度"两档候选，跟对应领域关键词绑定，方便生成 Prompt 精准提示 LLM 该替换哪些词。
- **"语音识别错误"和"同音字近音替换"字面症状很像（都是字被替换成音近/形近字），但触发场景不同，别合并成一类**：前者的场景前提是"用户在语音输入，ASR 转写出的错"，只对这一档才需要按上面的轻/重严重度分设子类；后者的场景前提是"用户在打字，手误/习惯性打了同音字"，本身不需要轻重分档，是和口语化、简短等并列的独立风格。混用会导致"重度 ASR 该配反问澄清"这条规则被错误地套到普通同音字错别字上。

## 四、边界 / 兜底测试池设计

任何有能力边界的 Agent，benchmark 都不能只测"它能不能做好该做的事"，还要测"它会不会正确地不做不该做的事"——这是独立于前面几节的一整块，通常单独成池，用自己的正交维度设计（不复用能力池的 case_category），期望输出通常是"未调用任何工具/未执行任何操作"这类否定性信号。

**子类型的名额分配也要走"一、总体架构"里的精确配额思路，不是"平均分掉就行"**：兜底池同样应该先定一份权重表——业务上更高频出现的子类型（通常是日常闲聊、能力范围外查询）给更高权重，业务上明确重点防线但现实出现频率低的子类型（敏感/违规内容、真正无法消歧）也要保证有非零、够统计意义的最低名额，不能因为权重低就被最大余数法配到 0 条。这份权重表和"轮次分布"一样，属于必须写进设计草案给用户确认的判断项，不能自己假设"平均分"就是对的——不同 Agent、不同业务场景下这几类子类型该占多大比例，差异可能很大。子类型内部如果还有进一步分档（比如上面 ASR 错误的轻/重度），同一套精确配额思路要递归应用一层。

**典型子类型**（示例，具体取舍看项目场景）：

- **日常闲聊/寒暄**：用户说的是完全非任务性的招呼语/闲聊（跟"能力范围外查询"是两回事——闲聊压根不构成一次提问，谈不上"问了但答不了"），测试 Agent 能不能得体地简短回应/引导回正题，而不是生硬拒绝、也不是把闲聊话硬套进查询流程当真去处理。
- **指令误入**：用户发出的是该由别的模块执行的操作指令（而不是查询/咨询类），测试 Agent 是否正确识别"这不归我处理，也不能代为执行"。
- **越权诉求**：用户要的是超出这个 Agent 边界的综合建议/主动决策（而不是查具体数据），或者是该走其他协作方处理的申诉/操作类请求。
- **能力范围外查询**：跟这个 Agent 服务的核心业务完全无关的领域问题。
- **事实明显偏离/无厘头**：问题本身基于一个明显不成立的前提（比如问询对象根本不属于这个业务场景、或常识上不存在），测试拒绝编造答案、不接梗展开的能力，而不是煞有介事地"查"一个查不出意义的东西。
- **含糊指代真正无法消歧**：历史里故意让最后一轮**同时、地位相当地**引入两个不同话题，指代词无法唯一判断，正确行为是反问澄清，不是猜一个答案——这是层③"先例唯一性"约束的正式反例，两者要对照着看：层③是"不小心引入了竞争对象，属于构造缺陷"，这里是"故意引入两个竞争对象，属于测试目标本身"。
- **敏感/违规内容**：测试拒绝行为的边界。

**这几类子类型的"正确行为"形态并不相同，不能全部套同一套"拒绝模板"去设计和校验**，上面 6 个典型子类型大致落在 4 种形态里（新增子类型时也按这个思路先归类，不要默认套"拒绝"）：
- **说明 + 引导式兜底回复**（日常闲聊、指令误入、越权诉求、能力范围外查询）：告知"这个我处理不了"，视情况引导用户去对的地方/说法，语气克制友好，不是拒绝。
- **说明前提不成立，不接梗、不编造**（事实明显偏离/无厘头）：和上一组的区别是不需要"引导去别处"——问题本身站不住脚，直接指出前提有问题即可，不用假装这是个可以被别的模块解决的正常诉求。
- **反问澄清**（含糊指代真正无法消歧）：输出必须是疑问句，目的是让用户补充信息，不是拒绝。
- **直接、简短的拒绝**（敏感/违规内容）：不展开、不说教、不复述对方的具体诉求内容。

设计每个子类型时要先想清楚它对应哪种形态，reference_answer 的写法和自动校验规则都要按形态分别定义——校验反问类不能只查"没调用工具"，还要查"输出里有没有疑问句/澄清意图"，否则一句生硬拒绝也会被误判为通过。

**敏感内容的安全构造模式**（专门针对上面最后一类，务必遵守）：
- 不能让 LLM 自由生成具体的敏感描述，必须用**人工预先审定的、克制委婉的候选措辞列表**，代码里强制从列表选取而不是现场让 LLM 生成，控制生成风险的边界。
- 这类 case 的语言风格要**锁定为"清晰"**，不要走噪声改写流程——噪声改写（换种说法、口语化）有把措辞往更露骨方向"创造性发挥"的风险，锁定清晰是风险最小、最可控的呈现方式。
- reference_answer 要求直接、简短拒绝，不展开、不说教、不复述对方的具体诉求内容。

## 五、输出 Schema 设计原则

- **权威评估字段 vs 参考字段要分开**：权威字段（比如"预期应调用的工具/参数"）是靠代码逻辑精确推导出来的，用于自动化打分（工具选择准确率等），必须准确；参考字段（比如"预期的文本/卡片回复"）通常是基于本地 mock 数据反推出来的示例，不代表被测系统的线上真实返回（线上数据源可能和本地 mock 不一致），这两类字段的可信度不一样，不能混为一谈。
- **参考字段必须带免责说明**：写清楚它的作用边界（仅用于自洽性校验，不是 ground truth；线上真实数据可能和本地 mock 不同，但不影响用户会这样问）。这段说明应该是**固定文案，直接写进每条产出样本里**，而不是散落在文档里让人自己找——保证任何人拿到单条 case 都能看懂这个字段能不能信、信到什么程度。
- **兜底类型字段要有语义说明**：如果一个字段的取值决定了"这条 case 本来是否应该被实质处理"（比如 fallback_type 是否为空），也要在每条产出里带一句解释，不要求使用者去猜。
- **校验结果要随样本一起产出**：每条 case 都带自检结果（通过与否、具体问题描述），不管过没过都要写进最终产出，不能只在生成日志里打印完就丢——这样使用者能一眼看出哪些 case 有已知瑕疵，而不是误以为全部完美。

## 六、协作与调试流程

- **设计阶段先对齐、后动手**：涉及判断/取舍的维度设计（类目怎么拆、比例定多少、正交关系怎么排）必须整理成书面草案给用户审，不能自己拍板；用户没确认前不动手写生成代码、不跑批量生成（见"使用流程"里的强制停顿点）。
- **数字算错要主动指出**：用户给的具体比例如果自己加起来对不上（比如百分比不等于100%），要主动指出、给出几个候选方案让用户选，不能悄悄按自己理解改掉。
- **小规模先行**：先出验证集规模的数据（比如正式集的 1/10），人工过一遍，再谈全量生成。
- **调试时不要"重新生成看看运气"**：用户指出具体某条 case 有问题时，把这条 case 的完整原始数据（历史、当前轮、期望输出、用到的固定数据快照）拉出来逐字看，定位到具体是哪句 prompt 指令、哪行代码没堵住，而不是猜一个大概方向就去改。
- **在对的层次修**：先判断这是这一条 case 独有的问题，还是所有同类构造都有的共性问题——共性问题要改共享基础设施（所有相关能力都会用到的公共模块），不能只改暴露问题的那一个脚本；反过来，纯属某个类目自己的边界情况，也不要为了"通用"硬塞进公共模块，加不必要的复杂度。
- **改完写强制复现的小测试**：不能改完代码就直接相信、拿去跑全量——绕开随机采样，手工构造一个能精确命中问题分支的规格，单独跑一遍验证修复确实生效，再重新生成完整验证集。
- **共享基础设施改动要全量回归**：因为是所有相关产出共用的模块，修完要把所有关联的产出重新生成一遍人工抽查，不能只重新生成暴露问题的那一个。
- **顺带发现的无关 bug 不要顺手改**：调试过程中如果发现了被测系统本身既有的、超出当前任务范围的真实缺陷，如实告知用户、单独记录/上报，不要在当前任务里顺手一起改掉，避免范围蔓延、也避免把不该动的代码动了。
- **主力验证工具不可用时，找替代手段验证真实行为**：不能因为某个工具（比如浏览器预览）暂时不可用，就退化成只做静态检查然后声称"应该没问题"——想办法用等价的最小化手段（比如手写一个执行环境跑一遍产出物的真实逻辑）验证行为确实符合预期，如实告知用户用了什么替代验证方式、还剩什么没能验证到。

## 已知失败模式速查表

| 现象 | 根因 | 对应章节 |
|---|---|---|
| 历史推荐了一个数据快照里不存在的 ID | 缺少数据锚定指令 | 二·层②·正向捏造 |
| 历史一轮说"没有X"，下一轮又展示了X | 固定兜底话术套用到了非空状态 | 二·层②·反向捏造 |
| 用户问"那东西还在不"，答案唯一确定，但读者自己都判断不出指的是什么 | 最后一轮同时引入了两个不相关的候选对象 | 二·层③·先例唯一性 |
| 含糊指代问题，但历史里压根没提过这事 | 只要求"可以不紧邻上一轮"，没要求"必须真实存在" | 二·层③·真先例 |
| 反复问"还有别的吗"，回复一字不差重复 | 没有要求措辞随场景变化 | 二·层③·反车轱辘话 |
| 历史直接展示"第3步/第3个"，却没有第1、2步的展示记录 | 进度标记独立随机采样，和历史实际轮次脱节 | 二·层②·渐进式可见 |
| 追问类 case 被要求"追问的内容必须和历史问的支持性一致" | 把"结构续接"和"内容可答性"两个维度耦合了 | 一·耦合检测法 |
| 含糊指代 case 被硬造出一个"正确答案"，但其实两个候选同等合理 | 把"真无法消歧"和"能消歧但写得像不能"两类 case 混在了一起 | 四·含糊指代真正无法消歧 |
| 敏感内容类 case 的措辞越写越露骨 | 让 LLM 自由生成 + 走了噪声改写流程 | 四·敏感内容安全构造模式 |
| 重度语音识别错误 case 却要求模型给出一个确定的正确回答 | 把轻/重两档 ASR 错误当成同一种预期输出处理 | 三·ASR 分档 |
| 兜底池里敏感内容/真无法消歧这类子类型被分到 0 条名额 | 子类型配额没设最低保底，纯按权重走最大余数法 | 四·子类型精确配额 |
| 日常闲聊被当成一次真实查询走完整工具调用流程处理 | 兜底池缺少"日常闲聊"这个独立子类型，闲聊被归进了别的类目 | 四·典型子类型·日常闲聊 |
